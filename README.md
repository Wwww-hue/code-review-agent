# 代码审查 Agent

一个带验证闭环、策略选择、长期记忆的 LLM 代码审查 Agent。用户粘贴 JavaScript 代码，Agent 自动检查 ESLint 问题、代码结构、复杂度与格式，并通过工具调用自主决策检查深度与修复策略。

## 项目定位

这个项目不是"调 LLM 修代码"的套壳工具，而是一个有自主决策能力的 Agent：

- LLM 通过 tool calling 自主决定调用哪个工具、按什么顺序、何时结束
- 用 ESLint、AST 分析、Prettier 做客观验证，不依赖 LLM 自称"修好了"
- 记录每一步的工具调用和代码变化，把黑盒 Agent 变成可解释流程
- 跨会话积累"规则 → 修复方案"的成功率，形成长期记忆

## 核心特性

### 1. LLM 自主决策（Agent Loop）

流程不是写死的，而是把检查、修复、结束等能力封装成工具，由 LLM 通过 tool calling 自主决定调用顺序和终止时机。

### 2. 检查深度策略选择

Agent 有两种检查深度：

- `run_eslint`：快速检查，只跑 ESLint，适合简单代码
- `deep_check`：深度检查，跑 ESLint + AST 分析 + 复杂度检查，适合复杂代码

LLM 根据代码复杂度自主选择。实测面对多函数、嵌套逻辑的复杂代码，它会选 `deep_check`，一次发现 24 个问题（含 ESLint 查不到的未使用函数、高复杂度函数）；修复阶段换回 `run_eslint`，因为不需要每次都做深度分析。

### 3. 修复策略选择：确定性修复 vs LLM 修复

Agent 有两种修复路径：

- `auto_fix`：ESLint 自动修复，零 token 成本，适合机械问题（分号、引号、缩进）
- `fix_code`：LLM 手工修复，成本高，适合复杂逻辑问题（未使用变量、`eqeqeq`）

LLM 自己判断用哪个。实测它会先试 `auto_fix`，搞不定再切 `fix_code`。

### 4. 验证闭环 + 重试

每次修复后自动重新校验。如果还有报错，带着新报错重试。最多修复 2 次，避免死循环。

### 5. 双验证器：ESLint + Prettier

- ESLint：检查逻辑规范
- Prettier：检查代码格式

检查通过后，系统自动触发 Prettier 检查，两个都通过才算成功。

### 6. 单调递减约束 + 快照回滚

每次修复前记录快照。如果修复后报错数没下降（原地踏步或变多），立即回滚到上一版，并把回滚信息反馈给 LLM 引导换方案。

### 7. 长期记忆（规则 → 方案级，带置信度校准）

记录"规则 → 修复方案 → 成功率"的映射，存 localStorage 跨会话保留：

```json
{
  "no-unused-vars": {
    "加 void 操作符": { "success": 3, "fail": 1 },
    "删除未使用变量": { "success": 1, "fail": 4 }
  }
}
```

下次遇到同类规则，把历史经验注入给 LLM，引导它优先用高成功率的方案。注意这里记的是"方案"而不是"工具"——工具是手段，方案才是策略。

**置信度校准**：直接算 `success / (success + fail)` 会让"1 胜 0 负"显示 100%，误导模型。所以我引入 Beta 先验平滑，公式 `(success + 1) / (success + fail + 2)`，把小样本的成功率拉向中间。同时设最小样本阈值（>= 2 次），样本太少的方案不参与决策。

### 8. 过程可视化

- 时间线：每一步的工具调用、报错变化、是否回滚
- 每步 diff：点击展开，看这一步和上一步的代码变化
- 收敛曲线：报错数随步骤的变化，直观看到 Agent 在收敛
- 成本仪表盘：总步骤、各工具调用次数、回滚次数、总耗时

### 9. 其他

- 规则可配置（用户勾选 ESLint 规则，偏好本地持久化）
- 历史记录（localStorage 保存，分页展示）
- 修复率统计
- 一键复制修复后代码

## 技术栈

- 前端：React + TypeScript + Vite + Monaco Editor + react-diff-viewer-continued + recharts
- 后端：Node.js + Express + ESLint + Prettier + Babel（AST 解析）
- AI：DeepSeek（tool calling）

## Agent 工作流程

```
1. LLM 根据代码复杂度选择检查深度：
   - 简单代码 → run_eslint
   - 复杂代码 → deep_check（含 AST 分析 + 复杂度）
2. 有报错：
   - 第一次修复先调 auto_fix（确定性、零成本）
   - auto_fix 后仍有报错，调 fix_code（LLM 修复）
   - 修复后回到第 1 步
3. 检查通过后，自动跑 Prettier 格式检查
4. 两个验证器都通过 → finish
```

代码层加硬性终止条件做兜底：

- 无报错立即成功结束（不等 LLM 调 finish）
- LLM 修复超过 2 次强制结束
- 循环超过 10 轮强制结束
- 报错数不降则回滚

## 核心设计决策

### 为什么用工具做验证，而不是让 LLM 自己判断

LLM 会"自称修好了"，但实际可能没修好，甚至引入新错误。ESLint、AST 分析、Prettier 提供客观验证，这是 Agent 和普通 AI 补全的本质区别。

### 为什么代码层要有硬性终止

实测发现快模型会忘记调 `finish`，陷入循环。所以不完全信任模型的自我约束，在代码层加终止条件兜底。LLM 负责决策调哪个工具，代码负责兜底终止条件。

### 为什么设计两种检查深度

代码复杂度差异大，简单代码不需要 AST 分析和复杂度检查，复杂代码需要。让 LLM 自主选择检查深度，既保证复杂代码的检查质量，又避免简单代码的过度检查。这是"有代价差异的策略选择"。

### 为什么长期记忆记"方案"而不是"工具"

工具只有几个，记录"工具成功率"指导空间有限。而同一规则有多种修复方案（比如 `no-unused-vars` 可以"删除变量"、"加 void"、"导出变量"），记录方案成功率才能真正指导策略选择。

### 为什么长期记忆要做置信度校准

小样本的成功率不可信。1 胜 0 负显示 100%，会误导模型策略选择。引入 Beta 先验平滑 `(s+1)/(s+f+2)` 和最小样本阈值，避免小样本偏差。

### 为什么 ESLint / AST 放后端

浏览器端打包 ESLint 和 Babel 有已知的 Node 模块兼容问题（`window is not defined`、`node:path` 无法解析等），所以用极简 Express 接口跑 ESLint、Prettier 和 AST 分析。

## 快速开始

### 1. 启动后端

```bash
cd server
npm install
npm run dev
```

### 2. 启动前端

```bash
cd client
npm install
npm run dev
```

### 3. 配置 `client/.env.local`

```
VITE_LLM_API_URL=https://api.deepseek.com/v1
VITE_LLM_API_KEY=你的key
VITE_LLM_MODEL=deepseek-chat
```

### 4. 打开 http://localhost:5173

## 待改进

以下方向经过评估，当前场景不适用，故未实现：

- **Plan-then-Act（先规划再执行）**：当前任务简单（修 ESLint 报错），执行路径短，规划是过度设计。适合任务复杂、步骤多的场景。
- **规则文档 RAG 检索**：ESLint 是开源项目，规则文档已在 LLM 训练数据中，检索是重复劳动。RAG 适合"LLM 不知道的领域知识"，如公司内部规范。
- **报错聚类（按规则合并 LLM 调用）**：当前报错少、同规则重复低，合并省不了多少 token。且按规则拆分修复会与"每次修复后立即验证"的闭环冲突。适合报错量大、同规则重复多的场景。
- **文件系统操作（read_file / write_file）**：当前是"粘贴一段代码"的场景，Agent 操作文件需要处理路径校验、备份、写后验证，是另一个量级的工程。
- **支持 TypeScript / Vue 多语言**：属于配置扩展，非核心逻辑，优先级低。
- **支持审查项目文件而非单段代码**：需要处理跨文件依赖、import 解析、修复顺序，是另一个量级的工程。
